======================

PART 1 — paths-ignore: PREDICTION vs OBSERVED REALITY
===============================================================================

paths-ignore on push and pull_request:  docs/**, handoff/**, *.md

GitHub skips a run only when EVERY changed file matches. One source file in a
mixed commit forces a full run. Under GitHub glob semantics `*` does not cross a
`/`, so `*.md` covers ROOT-level markdown only — a .md nested under src/ would
still build. Deliberately conservative.

GitHub actually did:

f97dd28 is the commit that motivated this fix: docs+handoff only, it burned
~37 minutes of native runner time. All 16 of its files match the ignore list, so
under the corrected workflow its push run would not have been created at all.

HONEST LIMITATION — pull_request semantics differ:
  The two documentation-only commits DID still produce a pull_request run
  (31372540845 for e689178, 31372647888 for ec45f66). GitHub evaluates
  paths-ignore for pull_request against the ENTIRE PR DIFF (base...head), not
  the newest commit, and this PR's cumulative diff contains ci.yml and the
  migration. That is expected GitHub behaviour, not a misconfiguration.
  An earlier revision of CURRENT_WORK.md claimed a docs commit "triggers no
  workflow run at all"; that overclaim was corrected in commit ec45f66 rather
  than quietly dropped.
  What Step 10 asked for still holds: a docs-only push to a branch WITHOUT an
  open PR -- the f97dd28 case -- is skipped entirely. Per-PR cost is bounded to
  a single matrix by Part 2.

PART 2 — duplicate runs of one commit (concurrency)
===============================================================================

BEFORE: group = ${{ github.workflow }}-${{ github.ref }}
  github.ref differs between the two events raised by one push to a branch with
  an open PR:  refs/heads/<branch>  vs  refs/pull/1/merge
  => separate groups => neither cancels the other => TWO full native matrices.

This was not merely wasteful. On commit e4749e6 the two matrices contended for
runners and each pushed the other past a timeout, in OPPOSITE jobs:

  job              push 31364937721            pull_request 31364972116
  ---------------  --------------------------  --------------------------
  Web / JS checks  success  1m51s              success  1m51s
  iOS Simulator    SUCCESS  25m21s             cancelled 30m45s (30m cap)
  Android          cancelled 45m13s (45m cap)  SUCCESS  44m40s

  The two Android jobs finished five seconds apart (07:57:56Z / 07:58:01Z) after
  both were dragged from a ~35 minute solo baseline to ~45 minutes.
  EVERY job passed in one run or the other, so the commit was sound; both
  timeouts were artefacts of the duplication, not defects in the code.

AFTER: group = ${{ github.workflow }}-${{ github.head_ref || github.ref_name }}
  head_ref is the source branch on pull_request; ref_name is the branch on push.
  Both events for one branch now share a group, so cancel-in-progress leaves
  exactly one matrix. Both events describe the same commit -> no coverage lost.

OBSERVED, three independent times:

  1. commit 3661d0a
     push 31369932367 created 08:24:32Z -> CANCELLED
       Web and Android cancelled at 08:24:38Z (3s in), iOS at 08:29:36Z
     pull_request 31369936191 created 08:24:35Z -> SUCCESS (survivor)

  2. commit 6820de9 (private repo, before going public)
     push 31368186633 created 08:00:26Z -> CANCELLED at 08:00:31Z, ONE SECOND
       after the sibling pull_request run entered the same group.
     Billing does not explain that: a billing block yields `failure` (which is
     exactly what the surviving run's jobs show), not `cancelled`.

  3. superseded head e689178
     pull_request 31372540845 -> CANCELLED when ec45f66 was pushed into the
     same group. Superseding a head no longer leaves an orphan matrix running.

Per the owner's instruction, a duplicate event being cancelled by the
concurrency rule is EXPECTED PASS BEHAVIOUR, not a failure.

PART 3 — public-repository fork-PR hardening
===============================================================================

  permissions: contents: read            (workflow level, least-privilege token)

  android + ios-simulator jobs gated on:
    github.event_name == 'push' ||
    github.event.pull_request.head.repo.full_name == github.repository

  => a FORK PR gets the cheap Web / JS job only: no native matrix, no secrets,
     no privileged behaviour.
  => OWNER WORK IS UNAFFECTED: every push to main and feature/**, and every
     same-repo PR, satisfies the condition. This withholds COST, never
     CORRECTNESS. A maintainer wanting full native coverage for a fork PR
     pushes the branch into this repo, which satisfies the same condition.

  The workflow uses `pull_request`, NEVER `pull_request_target`, and says so
  in-file. pull_request runs fork code with a read-only token and no access to
  repository secrets. Switching to pull_request_target to "make secrets
  available to PRs" is the classic fork-PR compromise. This workflow needs no
  secrets at all: the Supabase values are non-functional placeholders and the
  native builds prove compilation, not backend connectivity.
