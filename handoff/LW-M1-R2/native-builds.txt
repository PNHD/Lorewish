=== WHY THIS TOOK FIVE RUNS (full transparency, nothing silently retried) ===

1. Run 31348869607 (commit 6716f64): iOS job's scheme-discovery step picked `EXConstants` (a
   CocoaPods library subproject scheme) instead of the app's own `Lorewish` scheme — the heuristic
   ("first scheme not containing the literal string 'Pods'") was wrong, since library schemes don't
   contain that string either. Android job was still running when this was discovered and diagnosed;
   not force-completed.
2. Run 31349358407 (commit 17464e3, fixing #1 — scheme now derived from the workspace's own
   basename): iOS built successfully but the "Find built .app bundle" step used
   `find DerivedData/Build/Products -maxdepth 1 -name "*.app"`, one level too shallow — Xcode puts
   the `.app` at `Products/<Configuration>-iphonesimulator/<App>.app`, not directly in `Products/`.
   The build log's own directory dump (printed by the step's own error-fallback listing) showed
   `Lorewish.app` sitting right there, one level down — confirming the build itself had already
   succeeded. Separately, the Android job hit its 30-minute job timeout mid-compile (first-ever run,
   cold Gradle cache, nothing to restore from `actions/cache` yet) and was cancelled, not failed on
   its own merits.
3. Run 31350869242 (commit 8b0614a, fixing #2's maxdepth and raising Android's timeout to 45m): iOS
   now succeeded end-to-end — but its own screenshot showed React Native's own
   "No script URL provided. Make sure the packager is running..." error screen, not the app. This is
   `react-native-xcode.sh`'s standard, unconditional behavior for a Debug-configuration build on
   Simulator: it skips embedding the JS bundle entirely, assuming a live Metro server will be
   attached instead (true for local development, never true on a CI runner). The Android job failed
   after ~38 minutes with its own "Build debug APK" step never reporting a conclusion in the Jobs
   API — consistent with the runner process being killed rather than Gradle exiting with a normal
   error, and its log blob was never fully persisted (repeated `BlobNotFound` fetching it
   afterward) — diagnosed as disk-space exhaustion on the standard runner image (Android + Expo/RN
   native compilation from a cold cache is heavy; ubuntu-latest ships with several large SDKs this
   project never uses eating into the ~14GB free by default).
4. Run 31352831669 (commit c73b6f0, freeing disk space + adding `df -h`/`--stacktrace`
   diagnostics): all three jobs passed, including Android within its new 45-minute budget. This
   confirmed the disk-space diagnosis was correct. At this point the Android debug APK and iOS
   Simulator "app running, screenshot captured" evidence both existed — but the iOS screenshot from
   this run still showed the same RN "no script URL" error (same Debug-configuration cause as #3;
   the maxdepth/timeout fixes didn't address that, since it's a separate, unrelated cause). Verified
   locally (not guessed) that Android's generated `android/app/build.gradle` signs its release build
   type with the auto-generated debug keystore by default (Expo's standard behavior with no
   `credentials.json` present) before committing to the release-build-type fix for Android too.
5. Run 31354813415 (commit 5fd64d4, iOS switched to `-configuration Release`, Android switched to
   `assembleRelease`) — the run recorded above as final. Release configuration/build type always
   embeds the JS bundle regardless of platform (no Debug+Simulator skip branch applies), and Release
   needs no code signing on the simulator either way. This is also the standard, documented shape
   Appetize itself expects for uploaded simulator builds — not a workaround adopted only to make CI
   pass.
