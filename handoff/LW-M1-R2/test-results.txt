--- SSR env-var bug found and fixed during this task ---

`src/lib/supabase.ts` originally called `createClient(...)` at module scope, reading
`process.env.EXPO_PUBLIC_SUPABASE_URL` / `..._PUBLISHABLE_KEY` and throwing if absent. Expo Router's
static web export prerenders every route (including /account, and by extension every route since
AuthProvider is mounted in the root _layout) in a Node SSR pass that does not inline EXPO_PUBLIC_*
env vars the way the real browser/native bundle does — so the throw fired during prerendering and
broke `expo export -p web` for the whole app, not just /account. Fixed by deferring client
construction to first actual use (`getSupabaseClient()`, called only from effects/handlers that only
run in a real browser/native runtime). This also incidentally makes the client safe to import inside
the GitHub Actions native builds, which supply placeholder (non-secret) env values rather than the
real dev-project credentials.

--- Metro/web resolver false alarm (self-resolved) ---

An initial dev-server run showed `UnableToResolveError` for
`@supabase/realtime-js`'s `./lib/websocket-factory` on web, despite the file existing on disk. This
did not reproduce after clearing `.expo/cache` and restarting the dev server — attributed to a stale
Metro resolver cache from installing new dependencies while the server was already running, not an
actual package or config problem. No metro.config.js changes were needed.
